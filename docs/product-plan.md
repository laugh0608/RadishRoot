# RadishRoot 完整产品规划

文档基线：2.0 · 2026-10-13 · 已确认的产品方向与第一 MVP；后续阶段为待验证候选。

## 1. 名称与定位

- 项目 / 仓库：`RadishRoot`。
- 中文名：萝卜根系；完整产品称呼：RadishRoot OS。
- 标语：看见状态，理解操作。
- 定位：以可解释操作与结构化交互为核心的 Rust 实验操作系统。

Root 呼应系统基础、文件系统的根和原因追溯。“根系”表达资源与操作的关联，不承诺 UNIX root 权限语义或 Linux 兼容性。

RadishRoot 先成为能够真实使用、失败可诊断的小型系统。核心探索是：当资源、结果和操作记录拥有清楚的类型与关联，用户能否更容易理解计算机在做什么，并在界面与命令之间连续工作。

## 2. 首批使用者与场景

第一阶段服务项目所有者、系统开发者和愿意在虚拟机中试用的技术用户。验收使用合成数据与专用虚拟磁盘，不以承担个人主力资料或运行现有桌面软件为目标。

| 用户任务 | 产品行为 | 成功的可观察结果 |
| --- | --- | --- |
| 看懂机器与卷的状态 | 图形和终端查询同一服务 | 容量、只读、挂载等字段来自实际状态，未知值明确标识 |
| 用界面找文件，用命令处理结果 | 文件管理器与终端共享 FileService | 创建后列表刷新；目录联动由显式动作触发 |
| 理解一次失败 | 对操作编号展开阶段与错误链 | 看见失败对象、已完成步骤、已知副作用，不把推测当原因 |
| 保存并重新打开文件 | 写回、正常关机与重启读回 | 同一磁盘字节与预期相符，并由宿主独立复核 |
| 重现一个问题 | 固定环境、合成材料、证据编号 | 他人能按说明复现并区分环境失败与产品失败 |

## 3. 产品支柱

### 真实状态与解释

系统服务产生结构化事实，展示层把事实翻译成易懂文字。错误至少包含稳定错误码、阶段、目标、底层原因和部分副作用。无法确定的原因标为未知；建议动作与已经发生的事实分开。首版解释不依赖 AI，也不宣称日志完整性等同于安全审计。

### 结构化交互

命令返回有字段和类型的记录；筛选、选择和排序处理记录，最后才渲染文本或表格。文件管理器直接调用相同服务，不拼接 shell 字符串；结果可定位文件、打开详情或关联操作。

### 可控的本地状态

核心功能离线运行，文件使用通用格式存储，正常保存具有明确写回边界。失败时保留真实状态，不静默重置数据、不把半完成写入当作成功。首版没有突然断电下的事务保证，也没有用户态隔离；不承载敏感或不可替代资料。

### 小而完整的工作台

首版只做文件管理器、结构化终端和共享操作详情。每个新增功能优先贯通存储、服务、输入、渲染和错误路径，再扩展功能数量。工作台采用 Radish 家族 Workbench 气质；具体方案见 [MVP 规划](mvp-plan.md)。

## 4. 家族关系与独立边界

| 参考项目 | 借鉴方向 | 本产品的边界 |
| --- | --- | --- |
| RadishLex | 本地核心、薄平台适配、可解释操作 | 不移植输入法或同步系统作为开机依赖 |
| RadishMemory | 原始事实与派生视图分离、真实环境验证 | 操作记录不是跨重启记忆库，也不引入模型检索 |
| RadishAxiom | 明确类型、来源与证据 | 不把引入编译器或形式化证明列为首版门槛 |
| RadishFlow | Rust 核心、UI 与平台边界清楚 | 不整包复用桌面 UI 和宿主依赖 |
| RadishNexus | Golden Path 与相关对象追溯 | 不预建团队协作、插件平台或家族总线 |
| RadishX | Workbench 视觉与语义 token | 不照搬 Web 组件、参考截图或展示页装饰 |
| RadishLedger | 离线事实、明确数据语义、统一验证材料 | 不搬入账号、加密同步、复杂治理脚手架 |

兄弟项目是设计参考，不是隐式配置来源或运行依赖。将来若要共享库，先证明至少两个真实调用方需要同一稳定契约，再独立评估许可、发布、版本和维护责任。

## 5. 分阶段产品路线

| 阶段 | 目标 | 进入与退出依据 |
| --- | --- | --- |
| 当前第一 MVP：v0.1 | 固定虚拟机中的独立系统、双应用、真实文件、可解释失败、安装交付 | M0–M5、FR01–FR12、AT01–AT24 全部按 [MVP 规划](mvp-plan.md) 验收 |
| 后续候选 A：可持续使用 | 更好中文显示、输入体验、回收站或版本、问题诊断导出 | 第一 MVP 完成；依据实际使用问题选择有限范围，重新设计存储与验收 |
| 后续候选 B：系统隔离 | 用户态隔离、应用装载、权限或能力模型 | 有真实第三方应用需求；明确故障隔离目标与系统调用契约 |
| 后续候选 C：平台与连接 | ARM 或真机、网络和受限应用交互 | 有目标平台与驱动可行性证据，逐一增加支持矩阵 |

A、B、C 不是承诺交付顺序或版本号；不能自动视为当前待办。多核、GPU、完整桌面、POSIX、大规模包生态与把家族产品全部搬入系统，均需另立产品决定。

## 6. MVP 的完整性与预览边界

第一 MVP 的价值同时依赖真实磁盘、图形操作和结构化终端，不能仅以启动画面、内存文件系统或宿主模拟器替代。安装器保留在最终 MVP，放在核心体验稳定之后实现。

M0 是技术可行性门槛。M1 是内部预览检查点：能从已有开发镜像启动，在文件区查看目录，在终端创建文件，列表刷新，查看对应操作，正常重启后读回。M1 不代表功能范围和发布条件全部完成，也不以制作安装介质拖延第一次交互验证。

M2 与 M3 补齐用户流程和解释能力，M4 收敛稳定性与资源边界，M5 完成安装与交付。任何预览对外提供前都需单独的发布范围、许可和实际证据决定。

## 7. 产品成功标准

1. 一个新试用者能按说明在固定虚拟机配置中完成安装、启动与演示，不依赖开发者本机的隐藏状态。
2. 文件管理器和终端对同一操作具有相同校验与结果；界面切换不导致数据语义变化。
3. 用户能从失败结果进入同一操作的详情，识别失败阶段和已知副作用；错误后仍可执行允许的查询。
4. 保存成功遵循文件系统及块设备写回契约；正常重启后文件由独立方式验证。
5. 主路径和关键失败路径有可复验材料；预览、模拟、真实 QEMU 和最终交付的证据不混用。
6. 产品没有依赖未来网络、AI 或家族服务才能成立的基本操作。

定量门槛、输入延迟、资源上限和循环次数只在 MVP 规划维护；产品文档不复制另一份数字。

## 8. 投入、范围变更与停止规则

按单维护者串行推进，不把多个项目间的空余时间等同于全职排期。实施前记录每周可投入小时；M0 完成后依据实际工时重估后续任务，预留平台接入返工时间。每次交接留下当前可运行入口、最后一次证据和下一项任务。

M0 若无法证明真实磁盘写回与独立读回，优先定位或替换不兼容组件，不用扩大 UI 范围掩盖阻塞。后续出现新想法，先判断是否改善当前 Golden Path；不相关需求放入候选池。安全边界、存储契约或平台变化必须同步正式范围、任务和验收，不能只更改实现。

## 9. 许可与交付

原创许可尚未决定；本轮不自行套用兄弟项目许可证，不声称已经开源或可以公开再分发。第三方代码、固件、字体和安装介质须按实际引入版本登记来源与分发条件。第一 MVP 的交付内容与发行阻断见 MVP 规划，治理细则见[许可与来源](governance/licensing-and-sources.md)。
