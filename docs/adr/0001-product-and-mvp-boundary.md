# ADR 0001：RadishRoot 定位与 MVP 开发顺序

日期：2026-10-13。状态：已接受的产品与规划方向；实现、组件冻结与验收尚未开始。

## 背景

项目已选择 Rust、固定 QEMU、复用引导 / 磁盘 / 分区 / 文件系统组件，以及可解释系统和结构化终端方向，并要求文件管理器与终端 UI。早期方案把完整图形联动集中在 M4，反馈较晚；参考家族项目后，需要沿用明确领域类型、真实证据与工作台视觉，同时控制治理和抽象规模。

## 决定

1. 命名 RadishRoot（萝卜根系），完整称呼 RadishRoot OS。
2. 保留真实存储 M0 门槛，M1 提前贯通图形列表、终端写入、操作详情、正常关机及独立读盘；仅作为内部预览。
3. 按文件工作流、查询与解释、稳定性、安装交付逐层扩展；完整 MVP 仍覆盖原始安装、持久化、文件管理与终端目标。
4. 采用明确领域类型，公共错误、身份与结果投影共享；不优先实现万能对象、插件平台或家族应用运行底座。
5. 宿主视图用于快速迭代，真实 QEMU / GUI 与独立磁盘验证是对应能力的完成门槛。
6. 采用家族 Workbench 原则，本地绘制映射；英文界面和 UTF-8 保真维持首版范围。
7. 文档分为产品、MVP、current、开发 / 治理、ADR 和月度 devlog；前期不预建业务代码、空检查或远端流程。

## 考虑过的其他顺序

先完成全部内核与串口能力再做 UI，会延迟用户价值验证。先做完整宿主 UI，再接真实盘，会掩盖底层不可行性。因此选择 M0 风险验证后立即实现最小真实交互，再逐层补齐。

## 后果

M1 集成工作比原计划更早，需要最小输入、渲染、服务和电源同时成立，但不要求完整查询 / 文件操作 / 安装。早期代码不能是一次性演示分支，后续能力必须扩展同一服务与视图。文档 2.0 重编 T / AT，历史编号必须附版本。完整范围、任务与验收只在 [MVP 规划](../mvp-plan.md)维护。

## 尚未决定

精确依赖版本、Live 来源、原创许可、实际工具与资源预算、正式发行版本和远端配置按相应实施节点冻结。本 ADR 不表示这些已验证或授权外部写入。
